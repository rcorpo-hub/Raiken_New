# Dependency selection and compatibility plan

Date checked: 2026-11-02. No package was installed/downloaded into the project and no lockfile was created. The recommendations below are a documented baseline, not a tested dependency matrix. Resolve exact stable patches, peer dependencies, advisories and licences immediately before approved implementation; pin the selected package manager and commit the resulting lockfile.

## Baseline from current official documentation

Official Next documentation displayed 16.4.3; React's version page lists 19.3; Tailwind docs display 4.3; Zod docs display stable 4.6; pnpm docs list release line 12. These are observations of current documentation, not installed versions. Node 24.x is a deliberate supported baseline; do not rely on a changing Vercel default. Use stable published dependency releases, not independent canary/RC selections.

## Compatibility gates before installation

1. Resolve exact stable Next/React/DOM/TypeScript/types releases; read peer requirements and current security advisories. Do not treat independently choosing the newest of each as proven compatibility.
2. Verify Tailwind/shadcn/Radix/React, RHF/Zod/resolver and Motion/Lucide combinations in one small synthetic form/admin preview after implementation approval.
3. Current combined browser baseline must include at least Tailwind's requirements: Chrome 111+, Safari 16.4+, Firefox 128+. Confirm actual customer device needs before locking the frontend baseline.
4. Verify Node 24.x across local/CI/Vercel and relevant workers. Current Vitest guide requires Node >=22.12 and Vite >=6.4; confirm exact selected versions instead of copying an old setup.
5. Pin pnpm's exact stable version and validate Vercel's selected executable in build output. Avoid an unqualified override command that accidentally picks an older manager. Use frozen installs and review lifecycle scripts.
6. Supabase SSR auth/proxy/cookie handling must match the selected Next release. Read version-matched installed framework docs during implementation. No user data in static caches or build-time fetches.
7. Prove direct storage uploads work with allowed 10MB documents; do not funnel them through the Vercel 4.5MB Function request limit.
8. Use one migration/type authority. Defer an ORM, global state library, microservice layer, realtime subscription infrastructure or separate CMS vendor until a concrete requirement justifies it.

## Additional capabilities requiring selection

Email transport, malware scanner, key-management service, error tracking, marketing delivery and any SMS/calendar/payment service need owner approval of capability, data processing, account, cost and region. Prefer supported real integrations, not a UI that falsely reports delivery/scanning. The planning restriction takes precedence over provisioning instructions in tooling guides; no resource or dependency was installed here.

For each approved dependency record purpose, exact version, licence, transitive footprint, maintainer/support status, security-advisory outcome and update owner. Pin tooling/actions, schedule reviewed update PRs and test them in previews. A package's popularity is not a selection criterion.
